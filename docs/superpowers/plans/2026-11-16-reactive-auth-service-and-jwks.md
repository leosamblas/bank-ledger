# Reactive Auth Service and Decentralized JWKS Validation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a dedicated Spring Boot `auth-service` with Argon2id password hashing and RS256 JWKS asymmetric token signing, decentralize JWT verification in all business services, fix endpoint security vulnerabilities (BOLA/IDOR in `query-service`, unauthenticated `ledger-service` endpoints), and update infra orchestration.

**Architecture:** Hexagonal architecture for `auth-service`; RSA 2048 keypair generation with public JWKS exposed at `/.well-known/jwks.json`; canonical in-memory JWKS public-key caching and token validator in `platform-commons`; removal of credential storage from `account-service` into isolated `auth_db`; endpoint vulnerability fixes in `query-service` and `ledger-service`.

**Tech Stack:** Java 25, Spring Boot 4.1.2 (Spring 7 / Spring Security 7), Bouncy Castle (Argon2id), Jackson 3, PostgreSQL, Flyway, Docker Compose, Nginx.

**Spec:** `docs/adr/0006-reactive-auth-service-and-token-introspection.md`

## Global Constraints

- **Language & Runtime:** Java 25 with preview features enabled (`--enable-preview`), Spring Boot 4.1.2.
- **Password Hashing:** Argon2id with OWASP parameters: memory $m = 19\text{ MiB}$ (19456 KiB), iterations $t = 3$, parallelism $p = 1$, salt length 16 bytes, hash length 32 bytes.
- **Asymmetric Tokens:** RSA 2048 with RS256 signature and JWKS format (RFC 7517).
- **MFA:** Explicitly excluded from implementation per user request to simplify automated testing.
- **Decentralized Validation:** Zero network calls for routine JWT verification in business services; in-memory public key cache.
- **Zero Breaking Changes for Web UI:** Response shape of `/api/v1/auth/login` must match `TokenResponse` (`token`, `expiresIn`, `tokenType`, `user`).
- **Endpoint Security:** All user data access must enforce object ownership verification (BOLA/IDOR prevention).
- **Infra Cleanup:** At the end of implementation, clean up running containers and volumes (`docker compose down -v`).

## Review Focus

1. **BOLA/IDOR in Query Service:** A client holding token for Account A requests `/api/v1/queries/accounts/{accountB}/balance` or statement. Expectation: HTTP 403 Forbidden.
2. **Argon2id Hash Compatibility:** Verify that Argon2id hashes generated by `auth-service` validate reliably and resist timing attacks.
3. **JWKS Token Validation:** Ensure token signed with private RSA key in `auth-service` is verified using public key in `account-service`, `transaction-service`, and `query-service`.
4. **Internal Ledger Protection:** Verify `/internal/v1/ledger/**` cannot be accessed anonymously.
5. **Account Provisioning Flow:** When a new account is registered via `/api/v1/accounts`, credentials are securely registered in `auth-service` with Argon2id.
